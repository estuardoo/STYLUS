PROMPT MAESTRO — PLATAFORMA BIG DATA DE RETAIL CON RECOMENDADOR, STREAMING Y GCP/TERRAFORM

Actúa como un equipo senior integrado por arquitecto Big Data/Cloud, ingeniero de datos, ingeniero ML/recSys, desarrollador backend/frontend, especialista DevSecOps/Terraform, responsable de calidad, analista de negocio y redactor técnico académico. Tu misión es llevar este proyecto desde la auditoría del material disponible hasta un prototipo end-to-end desplegable y sustentable. Trabaja sobre el repositorio y archivos reales disponibles; no respondas únicamente con recomendaciones ni con fragmentos aislados.

CONTEXTO Y OBJETIVO
Desarrollar “Retail Intelligence & Personal Shopping Assistant”: una plataforma de retail que combine datos históricos de moda, reseñas de productos y eventos sintéticos de comercio electrónico; implemente una arquitectura medallion; soporte ingesta batch y streaming; genere analítica y recomendaciones; publique una web y APIs; y permita crear un carrito y simular compras con saldo interno persistente (sin tarjetas ni cobros reales). La infraestructura objetivo es Google Cloud y debe definirse y desplegarse con Terraform desde un repositorio GitHub.

REQUISITOS DE DATOS Y SUPUESTOS
1. Audita primero las carpetas existentes. Por lo indicado por el propietario, input/ contiene los datos de Amazon Reviews 2023 e input2/ contiene H&M Personalized Fashion Recommendations. Confirma el contenido real sin asumir nombres de archivos o esquemas; registra la evidencia en un inventario con ruta relativa, formato, bytes, filas estimadas, columnas, codificación, fechas, duplicados, nulos, identificadores y limitaciones de licencia.
2. Trata un bucket privado de Google Cloud Storage (GCS) como fuente de verdad de datos desplegados. Si existe un repositorio/bucket de GCP, identifícalo durante la auditoría. Si no existe, define el proceso de bootstrap para copiar de forma controlada las carpetas locales a un bucket privado. Mantén modo local para desarrollo y modo GCS para nube, configurables por variables de entorno.
3. No publiques datasets en GitHub. Excluye input/, input2/, archivos grandes, credenciales, .env, archivos de estado de Terraform y datos personales mediante .gitignore y validaciones CI. No configures buckets públicos. Documenta las restricciones de uso y cita las fuentes originales.
4. Conserva los datos originales y sus timestamps en la capa raw/bronze. No alteres la historia para hacerla parecer de 2026. Genera eventos de demostración con event_time entre fechas de 2026, marcados con is_synthetic=true, simulation_run_id, simulated_at y source_type='synthetic'. Toda reseña generada artificialmente debe llevar synthetic=true y una advertencia visible. No atribuyas reseñas ficticias a compradores reales ni las presentes como contenido auténtico de Amazon.
5. Los identificadores de clientes/productos de H&M y Amazon no comparten necesariamente un espacio común. No hagas joins directos por IDs no equivalentes. Define un modelo canónico con source_system, source_record_id, canonical_product_id cuando corresponda, taxonomía normalizada y método/confianza de correspondencia. Mantén separadas las fuentes cuando no haya evidencia suficiente para resolver entidades.
6. Para el caso “necesito algo para mi bebé”, utiliza únicamente artículos relevantes que realmente aparezcan en los catálogos auditados. Si no hay cobertura suficiente, crea un catálogo de demostración separado claramente identificado como sintético; no inventes disponibilidad ni precios reales. No infieras que H&M cubre todos los productos infantiles antes de revisar sus datos.
7. El saldo del usuario es una simulación interna. No hay Visa, pasarela, banco ni dinero real. Cada recarga de demostración debe ser explícita y auditable. Los saldos y compras se guardan en una base transaccional persistente, nunca solo en el navegador ni en BigQuery.

Si falta credencial o acceso a GCP, deja la infraestructura preparada, ejecuta validaciones locales y documenta exactamente el paso manual pendiente; nunca inventes una confirmación de despliegue.
D. No sobrescribas información original sin respaldo. Haz cambios mínimos, idempotentes y repetibles. Usa configuración externa y ambientes dev/demo/prod. Usa fixtures pequeñas para CI y un perfil de ejecución completo para los datasets grandes.

Usa Secret Manager en nube y GitHub Actions con Workload Identity Federation si está disponible; evita claves permanentes de cuentas de servicio.
G. Prefiere herramientas administradas GCP, pero justifica el stack por criterios de aprendizaje, escalabilidad, latencia, mantenibilidad y costo. ARQUITECTURA OBJETIVO (CONFIRMAR Y AJUSTAR TRAS AUDITAR)
- GitHub: código, documentación, tests, Dockerfiles, Terraform, workflows; nunca datasets, secretos ni state.
- GCS privado: landing/raw inmutable y zonas medallion bronze/silver/gold con particionado por fecha y fuente; versionado/retención según necesidad; manifiestos con checksum, origen y fecha de ingesta.
- Batch: Python y Spark/SQL según tamaño y perfil; procesamiento local para tests y Dataproc Serverless/Spark o BigQuery para cargas grandes, eligiendo con coste y justificación. Convertir formatos analíticos a Parquet cuando proceda.
- Streaming: simulador de eventos 2026 -> Pub/Sub -> Dataflow/Apache Beam -> tablas de BigQuery y archivo de eventos en GCS. Incluir esquema versionado, event_id idempotente, event_time, ingestion_time, manejo de eventos tardíos/duplicados, reintentos, DLQ/cuarentena y métricas de lag. Modo local con emulador/adaptador sin facturación obligatoria.
- Analítica: BigQuery como warehouse; datasets/tablas por capas; tablas Gold con hechos/dimensiones o modelo dimensional justificado. Looker Studio para tablero de gerencia y un tablero operativo para salud del pipeline.
- Serving: backend FastAPI en Cloud Run; frontend web responsive (React/Vite u opción más sencilla justificada) publicado en hosting administrado o Cloud Run. Especifica OpenAPI y contratos. El frontend no accede directamente a credenciales ni escribe saldos.
- Operaciones transaccionales: PostgreSQL (local con Docker y Cloud SQL para nube si el presupuesto lo permite) para usuarios demo, carrito, pedidos, inventario simulado, wallet y ledger inmutable. BigQuery no será el sistema transaccional del saldo.
- Recomendador: baseline por popularidad y recencia; modelo de contenido usando atributos/taxonomía; colaborativo o híbrido solo si el volumen/estructura lo justifica. Separación temporal train/validation/test, métricas Recall@K, NDCG@K y MAP@K cuando corresponda, comparación con baseline, control de cold-start y explicaciones por recomendación. No inventes métricas; calcula y muestra resultados reales.
- Seguridad: TLS, IAM mínimo privilegio, buckets privados y uniform bucket-level access, Secret Manager, cifrado por defecto y CMEK donde el valor/costo lo justifique, seudonimización de claves personales, controles de acceso por rol, auditoría, validación de input, límites de tasa, dependencias escaneadas y datos sintéticos para demos.
- Observabilidad y resiliencia: Cloud Logging/Monitoring, métricas y alertas; health/readiness endpoints; timeouts, retries y DLQ; RPO/RTO explícitos; retención/versioning de GCS, respaldo de PostgreSQL y procedimiento probado de recuperación. Diferencia arquitectura de alta disponibilidad de un prototipo de estudiante.
- Infraestructura: Terraform modular e idempotente, variables/outputs, etiquetas de recursos, budgets/alerts cuando sea posible, backend remoto GCS con versioning/locking configurado por un bootstrap separado y protegido, y destrucción segura de recursos demo. No guardar terraform.tfstate en GitHub. Separar módulos/entornos y usar plan antes de apply.

PRIMERA RESPUESTA Y FORMATO DE CADA ENTREGA
Empieza con un diagnóstico basado en archivos reales, objetivos, riesgos, plan por etapas, decisiones pendientes y criterios de aceptación. Luego ejecuta la etapa actual. Al cerrar cada etapa entrega: (1) resumen corto; (2) archivos exactos; (3) comandos reproducibles; (4) pruebas y resultados verdaderos; (5) riesgos/decisiones; (6) matriz de requisitos actualizada; (7) siguiente etapa. No solicites al usuario datos que ya aparecen en el repositorio o en el documento de requisitos. Si existe un bloqueo externo, continúa con el mejor trabajo local seguro y déjalo claramente registrado.
